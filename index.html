THE CORE MESSAGE
Summary, what to learn deeply, and what not to copy blindly.

Introduction · The big idea

Do not only improve the answer. Improve the system that produced it—and preserve evidence about what worked.

Harness² keeps the base model weights fixed. It adapts the surrounding execution harness—instructions, tools, memory, skills, delegation and runtime behavior—based on observed executions.

Why “²”? One loop improves the agent’s harness for the current task; a second loop improves the process used to improve that harness across future tasks.

How the two loops fit together

The first loop improves the harness for one task. The second loop turns evidence from that task into reusable experience for later tasks.

LOOP 1 · TASK-LEVEL ADAPTATION
1. BaselineRun the task with the current harness H₀.
→
2. ProposeGenerate candidate harness changes.
→
3. ProbeRun candidates and compare their behavior.
→
4. ComposeBuild the task-specific harness H* from supported changes.
Evidence from the task · what helped, what failed, and why↓
LOOP 2 · CROSS-TASK IMPROVEMENT
5. ReflectExtract reusable lessons from the observed contrasts.
→
6. Update experienceImprove the library that guides future harness edits.
→
7. Next taskUse the improved improvement process to adapt a fresh H₀.
Keep this distinction clear: Loop 1 changes the execution harness for the current task. Loop 2 changes the experience used to improve harnesses on future tasks.

01
Why Harness² exists: harness improvement in an open world
The problem the research is trying to solve
⌄

Problem statement

Agents face new tasks, domains, files, tools and constraints at runtime. A harness tuned in advance on a fixed set of tasks may not generalize. For an unseen task, there may be no answer key, labeled validation set or reliable verifier to tell the system whether an edit improved the result.

What the paper conveys

Agent quality depends on both the model and the harness around it. Harness² treats the harness as an editable object and adapts it at test time. The base model weights stay frozen; the system improves prompts, guardrails, memory, skills, tools, subagents, scripts and plugins instead.

How it addresses the problem

  • Observe a baseline execution to see how the current harness behaves.
  • Propose different harness edits aimed at different kinds of weakness.
  • Run candidates on the same task under matched conditions.
  • Use differences in trajectories and deliverables as evidence—not as a ground-truth correctness score.
  • Retain only lessons supported by observed contrasts for future tasks.
Important distinction: “No ground-truth verifier” does not mean “no evidence”. It means the method uses behavioral evidence from controlled comparisons, while acknowledging that this evidence is imperfect.
Recommendation: Think of Harness² as test-time adaptation of the agent’s operating system, not model fine-tuning and not simply prompt rewriting.

02
The two harnesses: execution vs improvement
The naming distinction that makes the whole paper click
⌄

Problem statement

It is easy to confuse the harness being edited with the mechanism doing the editing. If both are called “the harness”, the architecture becomes difficult to reason about.

What the paper conveys

  • Execution harness (H): the actual runtime configuration used by the task-solving agent.
  • Improvement harness (R): the editor/composer/reflector instructions and the accumulated library that guide how H is changed.

The improvement harness stays fixed during the task-level recursion for the current task. After the task, its library is updated. The next task starts from the common initial execution harness H₀, but the improved library R now guides how it is adapted.

How the two levels connect

Level 1 · Current task

Improve H

Try candidate execution harnesses, compare their runs and compose a better task-specific H.

Level 2 · Future tasks

Improve R

Reflect on the evidence, then update the experience library used by the improvement process.

How to reason about it

Imagine a coding agent with a weak tool-use instruction. H is the collection of files that tell the coding agent how to work. R is the improvement process that diagnoses the tool-use failure, tests candidate instruction changes, chooses a supported edit and records the lesson.

Not this: The previous task’s entire custom harness is blindly carried into the next task.
Recommendation: In your own architecture, name these objects explicitly—execution_harness and improvement_harness. Keep their state, permissions and versioning separate.

03
Propose–Probe–Compose: the core improvement step
How the system tests harness changes without a verifier
⌄

Problem statement

A harness editor can generate a plausible improvement, but how can it know whether the change actually helped when there is no answer key? Editing based on intuition alone risks adding irrelevant rules or introducing regressions.

Step 1 — Propose

First run the baseline harness to obtain a reference trajectory and deliverable. Then generate two candidate harnesses:

  • Invariant candidate: targets general agent behavior such as planning, tool use, context management or delegation.
  • Domain-specific candidate: targets professional knowledge, procedures and constraints relevant to this task/domain.

Step 2 — Probe

Execute each candidate on the same task with the same model and environment configuration. Compare its trajectory and deliverable with the reference. Did it avoid a failure? Use a tool correctly? Produce a more complete artifact? Introduce a regression?

Step 3 — Compose

A composer inspects the reference, candidates, diffs and execution evidence. It may merge supported changes, revise conflicting edits, adopt one candidate, or keep the original harness. It then runs the composed harness and records the decision and evidence.

Why “contrastive”? The evidence comes from comparing what happened under different harness configurations, not from asking a hidden answer key to score the task.
Do not overclaim: A better-looking trajectory is not proof of correctness. The paper explicitly notes stochastic execution and shared model biases can make behavioral contrasts misleading.
Recommendation: Every proposed edit should point to a specific moment in a trajectory and explain how that edit would have changed the behavior. If you cannot identify the moment, the edit is probably speculative.

04
Parallel vs sequential recursion
Two ways to spend the refinement budget k
⌄

Problem statement

One propose–probe–compose step may not explore enough alternatives. The framework needs a way to spend more inference and execution budget to improve the task-specific harness.

Parallel recursion — explore wider

Collect baseline executions, create multiple invariant and domain-specific candidates, probe them, then run multiple independent composition sessions over the candidate pool. Each composition produces and executes a successor harness. In the paper’s implementation, k controls the width of one population update.

Sequential recursion — refine deeper

Run a contrastive step, carry its refined harness and accumulated evidence forward, then run the next step on that updated state. Later rounds can retain, revise or correct earlier edits. Here k is the number of chained steps.

DimensionParallelSequential
Search shapeMany candidates/compositions from a shared starting pointOne evolving chain of refinements
StrengthBroader exploration and alternative combinationsLater steps can build on earlier discoveries
RiskMore concurrent compute; candidates may share blind spotsEarly mistakes can influence later steps
Meaning of kExploration widthNumber of successive steps
Recommendation: Start with k=1 to understand the basic loop. Increase k only when the task is valuable enough to justify the added model calls and execution cost. Choose parallel for breadth; sequential when iterative correction is useful.

05
Harnessing-level recursion: learning across tasks
How one task’s refinement can help the next task
⌄

Problem statement

Task-specific harness edits can solve the current task but do not necessarily transfer. Simply copying the whole edited harness to a new task can carry stale assumptions and task-specific facts.

What the paper conveys

After returning the deliverable, a reflector reviews the full improvement record: baseline runs, candidate harnesses, probes, diffs, composition decisions and selected output. It extracts lessons about which changes addressed which deficiencies, in what conditions and with what consequences.

What gets saved

  • The adopted executable harness.
  • An EXPERIENCE.md containing the situation where the lesson applies, what was learned and the supporting evidence.
  • An index so later sessions can find relevant entries on demand.

The next task starts from H₀ again. The library guides proposals and composition; components are selectively reused or adapted, not automatically inherited.

Example: “When a browser task requires exporting a dynamically filtered view, recompute derived state after every filter change” is a reusable procedure. “The button on this one page is blue” is not.
Key discipline: Adoption does not prove an edit helped. The reflector should decline to add a reusable lesson when the execution evidence is insufficient.
Recommendation: Treat the experience library as an evidence-backed engineering playbook, not a vector database of unverified tips. Store the cue, the actionable lesson and the traceable evidence.

06
The eight editable harness components
What the framework can actually change
⌄

Problem statement

If the harness is editable, what exactly is the editable surface? Treating everything as a prompt leads to bloated instructions and misses mechanisms that act inside the tool loop or support reusable workflows.

What the paper and repository expose

1. System promptAlways-on role, objective and core operating instructions.
2. GuardrailsConstraints, invariants and behaviors that should not be violated.
3. MemoryPersistent facts or guidance that should inform later runs.
4. Tool guidanceHow and when to use available tools, their inputs and expected outputs.
5. SubagentsSpecialized delegated workers invoked for bounded tasks.
6. SkillsOn-demand domain knowledge or repeatable multi-step procedures.
7. ScriptsDeterministic code for repeatable extraction, transformation or checks.
8. Plugins / middlewareRuntime hooks that can observe or constrain behavior inside the tool loop.

How to choose the right lever

  • Use concise always-on text for truly universal behavior.
  • Use a skill for a triggered procedure or domain knowledge.
  • Use a script for deterministic repetitive work.
  • Use a subagent when independent bounded work benefits from delegation.
  • Use middleware only when repeated evidence shows a behavior needs an enforceable runtime hook.
Recommendation: Match the fix to the failure. Do not solve every observed problem by adding another paragraph to the system prompt.

07
Evidence discipline: how to make useful harness edits
The practical engineering lessons hidden in the prompts
⌄

Problem statement

An improver can generate generic advice (“be thorough”), overfit to a one-off event, or encode a fact that was never verified. Such edits consume context and can damage future tasks.

What the implementation emphasizes

  • Trace every edit to a trajectory moment. State which run did what and how the proposed text would have changed it.
  • Prefer divergences. If two runs behave differently, the model has demonstrated the capability; a targeted instruction may help it use that capability consistently.
  • Use repeated concrete failures. A failure repeated across baseline runs is stronger evidence than a one-off anomaly.
  • Encode verified workspace facts directly. If a file mapping or unit is established by evidence, state the fact and label its scope. Do not merely tell the agent to rediscover it.
  • Keep procedures reusable. Store domain procedures at a scope where they remain valid, not one task’s peculiar facts.

Validation matters

The released prompt describes hard rejection conditions: every skill needs a trigger in always-on text; named scripts must exist in the proper location; malformed template syntax can break rendering; a harness must preserve the requested deliverable format.

Security note: The paper prompts treat task materials, trajectories and candidate artifacts as data, not instructions. Candidate code is inspected as text; it must not be blindly executed by the improver. This is essential when harness edits can add executable scripts or plugins.
Recommendation: Add schema validation, path validation, sandboxed execution, diff review and rollback before adopting a candidate in a production agent. Treat the improver as a privileged code-writing system.

08
What the experiments show—and do not show
Understand the results without turning them into hype
⌄

Evaluation setup

The paper evaluates professional tasks across WorkBuddy-Bench (office, web and code), JobBench (long-horizon professional work) and Harvey’s Legal Agent Benchmark (LAB). It tests frozen GLM-5 and Gemini 3.5 Flash executors with OpenCode and Codex harness configurations. The default harness editor is Claude Opus 4.8 under OpenCode.

Reported headline gains

+11.5WorkBuddy-Bench points, largest reported one-step gain
+4.5JobBench points, reported maximum one-step gain
+11.8 ppLAB partial pass-rate gain, reported maximum

Parallel recursion at k=5 adds further gains over a single step in the reported settings. The paper also finds reduced tool-error rates across its three benchmarks, although tool-call counts do not always decrease.

What you should conclude

  • Harness changes can materially affect agent performance even when model weights stay fixed.
  • Improving a weaker executor’s harness can sometimes close or reverse a model capability gap on a benchmark.
  • Scoped candidates, composition and the reusable library each contribute in ablations.
What you should not conclude: These are benchmark results on selected tasks, models and configurations—not a guarantee of improvement on your production workload. The method adds inference and execution cost, and the authors report regressions caused by poor selection, restrictive edits and noisy evidence.
Recommendation: Reproduce a baseline on your own task distribution. Track task success, regression rate, tool errors, latency, tokens and total cost—not just the best-case score.

09
Limitations, failure modes and open questions
Where recursive harnessing can go wrong
⌄

Problem statement

Recursive improvement can create an illusion of learning: the agent may mistake random variation for an edit effect, preserve a misleading lesson, or spend more compute than the improvement is worth.

Limitations identified by the paper

  • Extra cost: baseline runs, candidate probes, composition and reflection all add inference and execution work.
  • Noisy evidence: stochastic rollouts and shared model biases weaken causal attribution.
  • Transfer is uncertain: an edit that helps one task may not help another, even in the same domain.
  • Selection can fail: the selected deliverable may be weaker or narrower than another candidate.
  • Library growth: old or overlapping experiences can make retrieval noisy unless consolidated and maintained.
  • Fixed recursion budget: the current framework specifies recursion mode and k in advance rather than dynamically deciding when to stop.

Potential improvements

Use repeated probes for high-stakes changes, independent evaluation where available, explicit confidence and evidence links, regression tests, library expiry/versioning, and budget-aware stopping when new probes stop adding useful evidence.

Recommendation: In production, do not let a self-improving agent promote changes directly to its live harness. Use candidate → sandbox → evaluation → human or policy gate → versioned rollout → rollback.

10
How to explore the actual Harness² repository
A safe learning path from reading to running the demo
⌄

What the repository provides

The release implements parallel and sequential recursion, supports OpenCode and Codex executors, and includes benchmark integrations for JobBench, LAB and WorkBuddy-Bench. Its deterministic local demo can exercise both recursion modes without model credentials.

Prerequisites and local demo

The README specifies Linux, Python 3.12 and uv for the basic setup:

uv venv --python 3.12 .venv
source .venv/bin/activate
uv pip install -e '.[render]'
harness2-demo --output runs/demo --k 2

Model-backed benchmark run

For real benchmark execution, the README additionally lists Node.js 20+, Google Cloud CLI, model configuration and authentication. LAB and WorkBuddy have extra dependencies. Model-backed runs incur API costs, so start with one task and use dry-run to inspect selection.

cp .env.example .env
# Configure Vertex AI project and model IDs
gcloud auth application-default login

harness2-setup lab
harness2-check --bench lab
harness2 --bench lab --k 1 --mode parallel \\
  --only-domains antitrust-competition --max-tasks 1
harness2-judge --bench lab --k 1 --mode parallel
harness2-report --bench lab --k 1 --mode parallel

The judge/report commands must match the run’s benchmark, executor, subset, k, mode and seed. Check current repository docs before running because dependencies and interfaces can change.

Important operational warning

The README states executor network access is unrestricted by default and the Codex executor is run with its sandbox disabled. The project warns that public benchmark rubrics may be reachable online and recommends configuring network restrictions before evaluation to prevent access to benchmark answers or grading criteria.

Do not point this at production credentials or sensitive systems as a first experiment. Start in a disposable environment with restricted secrets, network egress and filesystem permissions.
Recommendation: First run the deterministic demo and inspect its run artifacts. Then read the setup, experiment and results/resume docs. Only after you understand the execution boundaries should you configure a model-backed benchmark.

Production-readiness checklist

Use this before allowing an agent to modify its own operating instructions or tools.

My overall take

The strongest idea in Harness² is not self-editing prompts. It is evidence-backed improvement of the improvement process itself.

The key architectural contribution is the separation of (1) task-specific harness refinement and (2) cross-task learning about how to refine. The Propose–Probe–Compose mechanism gives a practical way to compare candidate harness behavior when direct ground-truth feedback is unavailable. The library then attempts to convert those local experiments into reusable experience.

What I would learn deeply: the distinction between the two harnesses; how Propose–Probe–Compose works; why invariant and domain-specific proposals are separated; parallel vs sequential recursion; how the experience library avoids blindly inheriting task-specific harnesses; and the limitations of behavioral evidence.
What I would not copy blindly: unrestricted execution permissions, automatic adoption of self-authored plugins/scripts, or the assumption that better-looking trajectories imply correct outcomes. Production systems need stronger independent verification and governance.

Practice tasks: learn Harness² by building small pieces

Do these in order. They are deliberately small: each exercise isolates one idea, requires no model fine-tuning, and can be done with a toy agent or even a scripted mock. The goal is to understand the mechanics before attempting full recursive harnessing.

Recommended sequence: complete P1–P2 after Lessons 1–3, P3–P4 after Lessons 4–7, and P5 after Lessons 8–10. You can also complete all five tasks after reading the guide.

Practice rule: Do not let an agent automatically edit its live instructions or execute generated scripts. Work on copies, record every diff and manually approve changes.
P1
Build a baseline harness and record a trajectory
20–30 minutes · Understand what is being improved
⌄

Task

Create a tiny agent that answers questions about a small local folder of 3–5 text files. Give it a system instruction and two tools: list files and read a file. Ask it a question that requires reading more than one file.

Record

  • Its initial instructions and available tools.
  • The sequence of tool calls and their outputs.
  • The final answer and any unsupported claims.
  • Where it wasted time, missed information or made an incorrect assumption.

What you should learn

The execution harness is more than a prompt. It includes the tools and the environment, and the trajectory is evidence of how the harness behaved.

Deliverable: baseline.md with the task, harness version, tool-call trace and observed weakness.
P2
Run a manual Propose–Probe–Compose experiment
30–45 minutes · Understand the core algorithm
⌄

Task

Use the weakness found in P1. For example, the agent forgets to inspect all relevant files before answering. Create two candidate harness edits:

  • Invariant edit: a general instruction to plan the information needed and verify coverage before answering.
  • Task/domain edit: a file-research procedure that searches filenames, reads likely matches and cross-checks evidence.

Probe

Run the same task with the baseline and each candidate. Keep the model, task, tools and environment the same. Compare tool calls, evidence coverage, final answer quality and unnecessary work.

Compose

Choose the edit that is supported by the run evidence. If both help and do not conflict, combine them. If neither helps, keep the baseline. Write down why.

Deliverable: A one-page comparison table with baseline, candidate A, candidate B, observed difference and composition decision.
P3
Create an experience library for future tasks
25–35 minutes · Understand harnessing-level recursion
⌄

Task

Take the evidence and decision from P2. Write an EXPERIENCE.md entry with four fields:

  • When it applies: the task cue or situation.
  • Observed problem: what the baseline did.
  • Reusable lesson: the instruction or procedure that helped.
  • Evidence: which run and what difference supported the lesson.

Probe transfer

Create a second, slightly different question over the same folder. Start from the original baseline harness, retrieve the relevant experience and decide whether to adapt the lesson. Do not blindly copy the entire previous task harness.

Deliverable: One experience entry and a short note explaining whether it transferred to the second task.
P4
Try parallel and sequential refinement on paper
20–30 minutes · Understand width vs depth without extra compute
⌄

Task

Use one task and invent three plausible harness edits. Draw two strategies:

  • Parallel: test all three from the same baseline, then compare and compose.
  • Sequential: test one edit, carry the refined harness forward, then test the next edit against the new state.

Think through

What happens if edit 1 is wrong? Which strategy explores more alternatives? Which can build on a useful earlier change? Where could an early mistake contaminate later steps?

Deliverable: A simple diagram and a paragraph describing when you would choose each strategy.
P5
Map Harness² to your incident root-cause agent
45–60 minutes · Connect the paper to a realistic engineering system
⌄

Task

Take one historical alert or a synthetic incident. Write down the baseline agent's investigation steps: alert context, service identification, logs, traces, recent deployments, hypotheses, evidence and final Slack summary.

Choose one failure to improve

  • It queries logs with an excessively broad time range.
  • It misses correlation with a recent deployment.
  • It jumps to a root cause from one weak signal.
  • It posts a conclusion without linking supporting evidence.

Design the experiment

Choose the right harness component (tool guidance, skill, script or guardrail). Replay the same incident against baseline and candidate. Compare evidence coverage, false positives, diagnosis quality, time-to-diagnosis and cost. Record a reusable lesson only if the evidence supports it.

Safety boundary: Use historical or synthetic incidents, read-only telemetry and a mock Slack destination. Do not let the experiment run remediation or post to a real incident channel.
Deliverable: A mini Harness² design: baseline trace, proposed edit, replay comparison, adoption decision and one experience-library entry.
Suggested order: P1 → P2 → P3 first. Those three give you the essential Harness² mental model. P4 reinforces the recursion strategies. P5 is the bridge to a portfolio-quality engineering project.
